# Compatibility vectors for sync format 4

`sync-format4.json` is generated by `Aldune.Core` (the source of truth) and verified by `tests/Aldune.Core.Tests/SyncVectorsTests.cs`
on every run. A client that does **not** use `Aldune.Core` (Kotlin on Android, Swift on iOS) is compatible if it passes these
vectors **and** writes things that Core reads. If the format changes, Core's test goes red before any client does.

Regenerate (only if the format is changed on purpose; think first about the installed versions, see `docs/SYNC.md`):

```
ALDUNE_REGEN_VECTORS=1 dotnet test tests/Aldune.Core.Tests --filter "FullyQualifiedName~SyncVectorsTests"
```

## What the format says (what cannot be guessed by reading the JSON)

**Sync key.** 32 bytes. Written in unpadded base64url (`+`→`-`, `/`→`_`, no `=`); when reading it is accepted with
or without padding and must give exactly 32 bytes. The vectors use the key `00 01 02 … 1f`.

**Envelope (`envelopeJson`).** Unindented JSON, camelCase keys and case-insensitive reading:
`format` (4), `noteId` (GUID), `tombstone` (bool), `updatedAt` (ISO 8601 with offset, e.g. `2026-10-17T10:30:15.5+00:00`:
**.NET trims trailing zeros of the fraction**; when reading, any ISO 8601 with offset is valid), `deviceId`,
`cipherText`, `nonce`, `tag` (the three in standard padded base64). A client rejects `format` greater than 4 (clear message,
applying nothing) and less than 1.

**Encryption of a note's content.** AES-256-GCM, a random 12-byte nonce per encryption, a 16-byte tag, no associated
data (AAD). **What is encrypted is the base64 text (standard, padded) of the note's JSON, encoded as UTF-8** — not the
JSON directly. To decrypt: AES-GCM → UTF-8 text → decode base64 → JSON. Each vector's `payloadJson` is that
JSON already decoded.

**Note JSON (`payloadJson`).** camelCase keys: `id`, `text`, `color`, `createdAt`, `updatedAt`, `state`
(**number**: 0 active, 1 archived, 2 trash), `screenOrigin`, `tags` (list, may be missing), `isProtected`,
`protectedContent` (object or `null`), `protectedTitle` (clear text or `null`/absent: the visible name of a protected note, ≤ 60 characters, one line; ignored if the note is not protected), `dockPosition` (number or `null`). `pinnedToTop` (boolean, **optional**: written only when `true`; absent means `false`. It is the note being pinned to the top of the lists; a version that does not know it ignores it and, if it edits and re-sends the note, drops the pin). .NET writes non-ASCII characters as `\uXXXX`
(emoji surrogate pairs too): when reading, any valid JSON works. **After decrypting you must check** that the content's `id` and
`updatedAt` match the header's `noteId` and `updatedAt` (otherwise the note is rejected) and that a protected
note carries `protectedContent`.

**Deletion (tombstone).** The same envelope with `tombstone=true`. The encrypted content (same technique: base64 of the JSON) is
`{"id": <noteId>, "deletedAt": <updatedAt>}`. A deletion is **authentic** only if it decrypts with the key and its `id` and its
`deletedAt` match the header (`noteId`, `updatedAt`). One that is not **never deletes**: see `docs/SYNC.md` →
“Security model” and `SyncService.HandleUnsignedTombstones`. Vector `borrado con fecha falsificada` (deletion with a forged date).

**Protected note (`protectedNotes`).** It goes inside the note's JSON as `protectedContent`:
`{version: 1, salt, cipherText, nonce, tag}` (all standard base64). The key is derived from the password with
**PBKDF2-HMAC-SHA256, 600,000 iterations**, a 16-byte salt, 32 bytes of output; then AES-256-GCM (nonce 12, tag 16) of the
UTF-8 text **directly** (there is no base64 layer here). The number of iterations **does not travel in the data**: it is a compatibility
constant.

**Profile code (`shareCodes`).** Prefix `aldune-profile-v2:` followed by unpadded base64url of a UTF-8 JSON **with
PascalCase keys** (`Version` (2), `Key`, `Scope`, `NoteIds`, `Tag`, `ProfileName`, `Transport`, `ServerUrl`).
`Scope`: 0 all, 1 chosen, 2 tag. `Transport`: 0 folder, 1 server, 2 WebDAV (or `null`). It never carries the token.

**Version order (`versionOrder`).** `updatedAt` is compared first (the instant, regardless of offset) and, on a tie,
`deviceId` in ordinal order (UTF-16 units one by one, like `String.CompareOrdinal`; not cultural, and not by code point). The expected sign of `Compare(a, b)` is in `expectedSign`.

## Details that came up when porting to Kotlin (2026-10-17)

- **`expected` and `envelopeJson`/`payloadJson` write dates differently:** `expected` always carries 7 decimals
  (`...15.5000000+00:00`) and what is encrypted trims them (`...15.5+00:00`). Compare **as instants**, not as text.
- **The profile code is read case-sensitively** (`Version`, `Key`…; a camelCase one is rejected), unlike the envelope, which
  is read case-insensitively.
- **If the envelope carries no `format`, it is 4** (it is the property's default in Core).
- **Protected note password:** minimum 4 characters and not blank; it is encoded as UTF-8 before PBKDF2.
- **Profile code URL:** Core normalizes it with `Uri.ToString()` (scheme and host in lowercase, empty path → `/`, default port dropped).
- **Order by `deviceId`:** no vector tells UTF-16 units from code points; the Kotlin client covers it with a test of its own
  (emoji versus U+FF5E). Nor are there vectors of the decrypted content of a deletion
  (`{"id": noteId, "deletedAt": updatedAt}`; confirmed by reproducing the encryption byte by byte).
- **Two clients, one contract:** `kotlin-output.json` is written by `android/core` and read by Core (`SyncVectorsTests`). It changes on every run of the
  Kotlin test (random nonces and salts): still to be written only with an environment variable, as Core does with its own.

## Engine scenario vectors (`sync-scenarios.json`)

They are generated and verified by `tests/Aldune.Core.Tests/SyncScenarioVectorsTests.cs` with the real `SyncService` (a temporary folder as the store).
Regenerate only on purpose: `ALDUNE_REGEN_VECTORS=1 dotnet test tests/Aldune.Core.Tests --filter "FullyQualifiedName~RegenerateScenarioVectors"`.
It has to be done on Windows (the engine uses DPAPI). Spec: `docs/specs/2026-10-17-aldune-android-design.md` §6.

Each scenario (`scenarios[]`): `name` (E01…), `covers` (where it is in `SyncService.cs`), `settings` (local `deviceId`, `scope` 0/1/2, `tag`,
`noteIds`), `local` (`notes` with `authorDeviceId` —null = this machine's version—, `bases`, `tombstones`), `remote` (`envelopeJson` as it
was in the store, already encrypted, with `kind`, `key` and `plain`) and `expected`:

- `error` (null or text), `uploaded`, `downloaded`, `conflictsResolved`, `tombstonesApplied`: the counters of `SyncResult`.
- `remoteAfter`: each object left in the store (sorted by `noteId`): header, `rewritten` (did this pass write it?), and the **decrypted**
  note (`note`; null if it does not decrypt with the key) or `authentic` if it is a deletion. An object of unknown format comes out as
  `unreadable` and must stay intact. An object that disappears from the store means the pass deleted it.
- `localAfter` (notes with their author), `localTombstonesAfter`, `basesAfter`, `conflicts` (winner and loser: date, device, `tombstone`, text).

Rules for whoever consumes them: the keys are the vectors' one (`syncKeyHex`) and “other” (`otherKeyHex`); dates are compared as
**instants**; `"<now>"` is a date set by the clock (check only that it is recent); the bytes of an envelope, the
`id` and the date of the conflict are not compared (they depend on the clock). The scenario map is the one in spec §6.7.

Findings these vectors fix (Core's behavior today, not necessarily desirable): a remote deletion **without a signature** does not stay in the
store visible to the engine: it is ignored, removed from the store if the note exists here, and the note is **uploaded again** (E12a); with tag scope
the local deletion is uploaded even if the note no longer had the tag (E26); an edit against a deletion leaves a conflict even if the deletion wins (E27).

Still to add: E14 (cannot be set up with a folder: a single file per id), E21 (linked note without sync, needs setting up `NoteFileLink`),
the split between several versions of the same id (HTTP/WebDAV) and key rotation.

## What these vectors do NOT cover (and has to be covered before declaring the engine compatible)

The format ones (`sync-format4.json`) only fix the data. The **algorithm** is fixed by the scenario ones above, but they do not cover the
real transports or key rotation: that is tested separately, against a real server.

## Text, color and order vectors (`text-lines.json`, `text-color.json`, `text-order.json`)

They are generated and verified by `tests/Aldune.Core.Tests/TextVectorsTests.cs` (F3 of the Android spec) with Core's real functions, without touching them.
Regenerate only on purpose: `ALDUNE_REGEN_VECTORS=1 dotnet test tests/Aldune.Core.Tests --filter "FullyQualifiedName~RegenerateTextVectors"`.
The output is deterministic (regenerating without changing Core does not change the files).

Each case is `{"op", "args", "expected"}`, one per line. `op` is Core's `Class.Method`; `args` are its parameters by name; `expected` is what
Core returned, already passed through JSON. Conventions of the translation to JSON:

- **Positions and cursors**: UTF-16 units (`string.Length`), the same as Kotlin's `String`. There are out-of-range cursors (`-1`, `len+5`) to fix the clamping.
  Cursors that split a surrogate pair (emoji) are not tested.
- **`(string Text, int Caret)`** → `{"text", "caret"}`; if the function returns `null` (`EnterContinuation`, `RemoveOnBackspace`, `Move`, `ToggleCheckboxAt`,
  `CheckboxOnLine`, `RestOutlineFor`, `OklchColor.FromHex`, `Luminance`, `Between`), `expected` is `null`.
- `Count` → `{"done", "total"}`; `NoteText.Split` → `{"title", "body"}`; `IndentLines`/`OutdentLines` → `{"text", "selectionStart", "selectionLength"}`.
- **`TextEdit`** (`UncheckAll`, `RemoveChecked`, `SettleToggled`) → `{"text", "changed", "map"}`, with `map[i] = MapIndex(i)` for each `i` from 0 to the length of the original text.
- **Enums as numbers**: `LineMovement.Move.direction` 0 up / 1 down; `NoteColorAssigner` `tone` 0 light / 1 dark / 2 both, `rule` 0 rotate avoiding neighbors / 1 rotate /
  2 most distinct / 3 fixed (in Core's enum the order is that: `RotateAvoidNeighbors`, `Rotate`, `MostDistinct`, `Fixed`).
- **Line breaks**: the texts carry LF, CRLF and mixes; `EnterContinuation` receives `newLine` (both). Core normalizes nothing: the port does not either.
- **`NoteTitleHelper`** uses Core's default placeholder text, `"New note"` (in the app the language sets it). In Kotlin it is a parameter.
- **Real numbers** (OKLCH, distances, luminance, `Between`): written in the shortest format that recovers the same `double`. Compare them with a small
  tolerance (1e-9 relative); `#RRGGBB` values are compared **exactly**. If a hex differs by one unit in a channel because of the difference between .NET's `Math.Cbrt`/`Math.Pow` and
  the JVM's, **do not widen the tolerance silently**: it is a finding that has to be noted.
- `NoteColorAssigner.Assign`: `themeId` (built-in) or an inline `theme` (`{id, name, dark, light}`); `dockColors` are the deck's colors in order.
  `NoteThemes.Resolve`/`Sanitize` receive `custom` (a list of custom themes) when needed.

Core quirks these vectors fix as they are (they are not errors of the port): `EnterContinuation` only continues or ends a list with the cursor at the **end** of the line;
when ending an empty list (task or bullet) the line is left empty: the indentation is lost too (`TrimEnd`); `TaskLines.PrefixLength` is 1 if there is no space after the glyph;
`SettleToggled` moves nothing if any task in the list has subtasks; `Outdent` counts a tab as one level; `LineMovement` swaps contents, not line breaks;
`Between` returns `null` when the neighbors no longer admit a number between them.

**Outside these vectors** (covered separately): `NoteSearch` (Android folds accents and Core does not, so hand-written tests in Kotlin), `ColorFit` and `ColorMix`.

**App palette (F3b, `text-color.json`)**: `AppPalette.For` (mode 0 dark, 1 light, 2 system, 3 pastel, 4 midnight, and `windowsUsesLight`) returns the full dictionary of keys→color
(`#RRGGBB` or `#AARRGGBB`, **alpha first**, like Android's `Color.parseColor`); `AppPalette.IsLight` for modes 0-10. `AppPalette.For` also accepts `aspectColors` (slot id → hex) and modes 5-10 (retro looks: XP, Telecom, Bash, Phosphor);
`AspectCatalog.Retro` and `AspectCatalog.Resolve` fix the catalog (slots, swatches, Bash palettes, suggested theme); `ColorFit.*` and `ColorMix.Toward` fix the contrast adjustment and the mix.
